# Decisions log (ADR-style)

Why the kit is the way it is. Each entry: context → decision → rationale →
alternatives. Append (don't rewrite); supersede with a new entry when reversing
one. This captures the reasoning from the kit's design conversation so any agent
has the intent, not just the diff.

---

## D1 — Encode the whole delivery pipeline as skills + subagents + commands
**Decision:** Represent ideation→requirements→scaffold→design→backend→infra→ship
as focused, on-demand skills, with subagents per role and commands as entry points.
**Rationale:** Matches how the work actually decomposes; skills load by relevance
so context stays small; reusable across projects. **Alternatives:** one giant
prompt (context-heavy, rots), bespoke scripts (not adaptable).

## D2 — Stack defaults: KMP/Compose + Supabase + Cloudflare + Firebase + (Stripe)
**Decision:** Bake the user's real stack as defaults; Worker only when server
logic/secrets exist; two environments everywhere. **Rationale:** Eliminates
repeated configuration; templates derived from the user's proven myFinance
workflows. **Alternatives:** stack-agnostic generator (too vague to remove toil).

## D3 — Minimize human toil; "human must do" is an explicit, ordered checklist
**Rationale:** The user's core ask. The agent does everything automatable; the few
account/credential steps are surfaced, never buried. Drives `SECRETS.md` + onboard.

## D4 — Design: repo MANIFEST is the source of truth; visual tools are viewers
**Context:** AI-kick-started design rots; per-screen HTML generated by the coding
agent burns tokens and gives a worse multi-screen view. **Decision:** Keep
`design/` (DESIGN.md + W3C tokens + per-screen specs + catalog + screen-map) in the
repo; tools render from it. **Rationale:** Stops drift, keeps identity portable
(no framework switch), moves token-heavy rendering out of the coding agent.
**Alternatives:** treat the design tool as source of truth (lock-in, drift,
re-design per framework). Supersedes the earlier bespoke `tokens.json`-only idea.

## D5 — Stitch (MCP) is the programmatic design surface; Claude Design is manual
**Context:** The user wants a fluid loop: talk to agent → see designs → ask for
changes, without leaving the conversation. **Finding:** Claude Design has no
API/round-trip (handoff is a manual export); Stitch ships an MCP server with
generate/fetch tools. **Decision:** Default to Stitch-via-MCP for the fluid,
incremental loop; support Claude Design as an agent-guided manual canvas; choose
per project in `design/config.yml`. **Rationale:** Only Stitch can be driven
programmatically today; both share `DESIGN.md` so they're interchangeable.

## D6 — Per-screen targeting via stable screen IDs + fingerprint diff
**Context:** A Claude Design handoff bundle contains ALL screens; how does the
agent know which to apply? **Decision:** Key everything by a stable screen ID; the
user titles the artifact with that ID; `screen-map.json` maps tool titles ↔ IDs;
the agent applies only screens whose fingerprint changed and reports the rest as
unchanged. **Rationale:** Targeted, drift-safe, no full re-handoff. **Alternatives:**
re-apply everything (drift), manual diffing (error-prone).

## D7 — Claude Design token cost is on the Claude subscription, not the agent
**Rationale:** Corrected an earlier worry — designing in Claude Design/Stitch uses
their budgets; the coding agent only consumes the result. So the in-agent HTML
preview is demoted to an optional fallback (Flow C), not the default.

## D8 — Living, queryable docs as compressed state
**Decision:** `project-docs` maintains `STATE.md` + per-feature docs + changelog,
updated as part of every change; `/status` reads them. **Rationale:** Lets agents
(and humans, and external design tools) get current state without re-deriving it;
also a token-efficiency lever. A change isn't done until docs match.

## D9 — Feature lifecycle covers iterate/refactor/deprecate, not just create
**Rationale:** Most work is iteration. `feature-lifecycle` reads current state
first and updates it after; additive migrations; one feature per PR.

## D10 — MCP scope model enables parallel multi-project reuse
**Decision:** User-scope for account-wide/stateless servers (GitHub, Cloudflare,
Stitch, Playwright, Context7, Firebase) set once per machine; project-scope for
Supabase (pinned to a `project_ref`). **Rationale:** Same machine can run many
projects in parallel; shared servers don't conflict; each project keeps its own DB
binding. **Alternatives:** all project-scope (duplicated setup), all user-scope
(Supabase can't be multi-project).

## D11 — Include Playwright + Context7 (free); auth via stored session
**Rationale:** Playwright verifies the running build matches the design + e2e;
Context7 prevents stale-API rework (token saver). For login-gated apps, mint a
Supabase session for a staging test user and save `storageState` (avoid
automating Google consent). Both optional but on by default.

## D12 — Firebase/Google are largely CLI-automatable
**Correction:** Earlier claim ("no API") was wrong. `firebase`/`gcloud` create
projects, apps, service accounts, and run App Distribution; a Firebase MCP exists.
Only the OAuth consent-screen first-time config may need one console step.

## D13 — Secrets: one home per secret; GitHub Actions canonical, local mirror readable
**Context:** User wants GitHub-only to avoid duplication, but also to "read back" —
yet Actions secrets are write-only. **Decision:** Gitignored local mirror is the
readable source; pushed to GitHub Actions via `gh secret set`; committed manifest
is the names-only index; local-MCP secrets live once in the shell/keychain.
**Rationale:** No duplication, still readable, nothing secret committed.

## D14 — Tool-agnostic via neutral `.agents/` + `AGENTS.md` + symlink adapters
**Context:** User explicitly does not want Cursor- or Claude-specific lock-in.
**Finding:** No single universal directory standard exists; `AGENTS.md` and the
`SKILL.md` format are the closest neutral standards. **Decision:** Canonical
content in `.agents/`; `bin/link.sh` symlinks into `.cursor/.claude/.codex`.
**Rationale:** One source of truth, runs anywhere; the shim is the honest price of
no perfect standard. Supersedes the earlier `.cursor/`-based layout.

## D15 — Ship as a standalone, self-documenting, self-improving repo
**Context:** The kit should be its own GitHub repo, openable by any LLM with full
context, and self-maintaining. **Decision:** Standalone repo with `AGENTS.md` +
`docs/` (HOW_IT_WORKS, DECISIONS, ARCHITECTURE, GLOSSARY) + `kit-maintenance`
skill + `CHANGELOG.md`; `bin/publish-as-new-repo.sh` extracts it (cloud agents
can't create repos directly). **Rationale:** Portability, continuity, and any-LLM
maintainability.

## D16 — Behavior presets + token-efficiency + parallel-agents as first-class
**Rationale:** The user wants to set tone ("behave like X"), control cost, and use
multiple agents effectively. Encoded as `/mode` + `.agents/behaviors/*`, the
`token-efficiency` skill, and the `parallel-agents` skill, all referenced by
`AGENTS.md`.

## D17 — Brownfield path: adopt existing projects, not just bootstrap new ones
**Context:** The kit was greenfield-only (`/new-project`); a huge share of real
work is on codebases that already exist. **Decision:** Add a brownfield mirror of
the bootstrap pipeline — `project-adoption` (`/adopt-project`) as a sibling
orchestrator that **detects** the real stack + **reverse-engineers features** from
routes/screens/endpoints/tables, **reverse-documents** them into the same
`project-docs` state model (`docs/STATE.md` + feature docs), and reconciles
infra/MCP/secrets; plus three focused skills/commands — `code-audit` (`/audit` →
`docs/AUDIT.md`, read-only, with a `code-auditor` read-only subagent for fan-out),
`codebase-cleanup` (`/cleanup`, behaviour-preserving only), and
`improvement-planning` (`/propose-improvements` → routed `docs/ROADMAP.md`).
**Rationale:** Recover state from code instead of creating it from an idea, then
reuse the *entire* existing day-to-day toolchain (`/status`, `/add-feature`,
`/iterate-feature`, `/design`, `/ship`) unchanged — adoption is just the on-ramp.
**Key constraints:** (1) **stack-aware** — detect and respect the project's real
stack/conventions; apply the KMP/Compose `conventions` rules and managed infra
(Supabase/Cloudflare/Firebase) only where they match or the user opts in, never a
forced migration (contrast D2, whose defaults are for *new* projects). (2)
**code is the source of truth** — never document a feature/test/guarantee that
isn't really there; mark inferred items. (3) **separation of phases** — adoption
and audit are read-only; behaviour changes are deliberate, reviewable steps.
**Alternatives considered:** a single "review" command (too coarse — couldn't be
re-run per phase or routed); auto-migrating adopted projects onto the kit's stack
(rejected — lock-in and churn, violates "respect what's there").
